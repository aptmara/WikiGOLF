WikiGOLF 総合アーキテクチャ・設計仕様書

Wikipediaの記事本文から3Dゴルフコースを動的生成し、六次の隔たり（SDOW）を攻略するネイティブDirectX 11ゴルフゲーム

1. プロジェクト概要と思想（Philosophy & Background）

1.1 ゲームコンセプト：「Wikipedia × ゴルフ × 最短経路探索」

WikiGOLF は、インターネット百科事典「Wikipedia」の日本語記事データを動的に解析し、その記事の文字・構造・画像から3Dゴルフコースをプロシージャル生成してプレイする、まったく新しいアプローチのスポーツ＆パズルアクションゲームです。

プレイヤーは開始記事（スタートホール）からスタートし、記事本文中に存在する無数のハイパーリンク（青文字リンク）を目指してゴルフボールを打ち込みます。カップインしたリンク先の記事へとコースがシームレスに遷移（ロード・生成）され、最終的な目的記事（ターゲット）へと最短打数・最短遷移数で到達することを目指します。

コアゲームループ
  1. 記事のロード & 地形生成: Wikipedia API経由で記事を取得。HTML/CSSまたはテキストから高低差・マテリアル・テクスチャ・ホールを生成。
  2. ショット & コース攻略: クラブ（1W〜パター）を選択し、風向き・起伏・ライ（フェアウェイ/ラフ/バンカー等）を考慮してショット。
  3. リンクへのカップイン: 狙った記事リンクのカップ（旗）にボールが入ると、その記事へ遷移！
  4. ゴール到達（ゲームクリア）: 最短経路（Six Degrees of Wikipedia）の知識とゴルフテクニックを駆使し、ターゲット記事へカップイン！

1.2 開発経緯と思想の昇華（WikiPinballからWikiGOLFへ）

コードベース内（WikiPinballScene.h や WikiComponents.h）には、初期プロトタイプであった WikiPinball の痕跡が見られます。初期構想では「Wikipediaの記事の壁面を見出しやリンクの障害物に仕立て、フリッパーでボールを弾き当てるピンボールゲーム」として試作されました。

しかし、ピンボール特有のランダム性や反射制御の難しさに比べ、「狙ったリンクへ意図を持ってボールを運ぶ」「風や芝の抵抗を計算してクラブを選び抜く」というゴルフのゲームデザインの方が、Wikipediaのリンクを辿る探索（いわゆる「Wikipediaゲーム」や「六次の隔たり」）の知的な面白さと極めて親和性が高いことが判明しました。これにより、本格的な弾道シミュレーション・ライ判定・3タップゲージを備えた「WikiGOLF」へと大幅な昇華を遂げました。

1.3 技術スタック選定思想：ネイティブ志向・高レスポンス設計

UnityやUnreal Engineなどの汎用ゲームエンジンを採用せず、Win32 / DirectX 11 / C++20 によるスクラッチ開発を採用しています。この設計判断には以下の強い思想があります：

  • メモリとバイナリサイズの極小化: 数十MiBクラスの軽量フットプリントで軽快に起動・終了。
  • Webコンテンツ（HTML/DOM）の直接レンダリング制御: litehtml + Gumbo + DirectWrite + Direct2D を用いて、GPUテクスチャ上に直接CSSレイアウトを焼き込む特殊なグラフィックスパイプラインを完全制御。
  • 超高速なローカルグラフ探索: 約数GB規模の日本語Wikipediaリンクデータベース（SQLite）をプロセス内で直接扱い、双方向BFS（幅優先探索）をミリ秒単位で高速実行。

3.1 Entityのビット構成（18bit Index + 14bit Generation）

Entityは単なる uint32_t（32ビット整数）として表現されます。下位18ビットがインデックス（最大約262,144エンティティ）、上位14ビットがジェネレーション（世代、最大16,383回再利用可能）としてエンコードされています。

  • 世代番号チェック: 削除済みエンティティに対して古いハンドルからアクセスしようとした場合、IsAlive(entity) が直ちに false を返し、ダングリング参照のバグを完全に排除します。
  • 軽量破棄管理 (EntityOwner): コントローラーやシーン単位で生成したEntityをRAII方式で一括破棄できる ecs::EntityOwner を完備。

4.2 ショットシステム：本格3タップゲージ

多くの名作ゴルフゲーム（みんなのGOLF等）を踏襲した直感的な3タップ式ショットゲージを採用しています：

  1. 1タップ目（ショット開始）: パワーゲージが往復を開始。
  2. 2タップ目（パワー確定）: 狙いたい強さの位置でゲージを確定（0.0〜1.0）。
  3. 3タップ目（インパクト確定）: 高速で移動するインパクトカーソルを中央のターゲットゾーンで止める。

インパクトの誤差に応じて、4段階のショット判定（ShotJudgement）が下されます：

  • Special / Perfect (誤差 < 2%): 完璧なショット。狙い通りの方向・スピンで正確に飛翔。
  • Great (誤差 < 5%): 優秀なショット。ごく僅かなブレのみ。
  • Nice (誤差 < 15%): 良好なショット。実用的な許容範囲。
  • Miss (誤差 15%以上): ミスショット。弾道が左右に大きくスライス/フックし、飛距離も低下。

4.4 Par（基準打数）の動的算出ルール

従来の固定Parではなく、Wikipediaのリンク関係（SDOW最短ホップ数）に基づいて各ホールのParがインテリジェントに算出されます（ParRules.h）： 

// ターゲットまでの最小ホップ数が計算済みな場合
Par = std::max(1, minHopsToTarget + 1);

// 未計算・到達不能フォールバック時（有効リンク数から推定）
Par = std::clamp(static_cast<int>(validLinkCount) / 2 + 2, 3, 12);

「目標記事まで最短あと2回の記事遷移が必要なら、このステージはPar 3」のように設定されるため、プレイヤーは「最短ルートを通ればパーやバーディが取れる」という明快な目標感を持ってプレイできます。

5. Wikipedia API & SDOW最短経路探索（Wikipedia Pipeline & SDOW）

5.1 WinHTTPによるMediaWiki API通信アーキテクチャ

WikiClient クラスは、Windows標準の WinHTTP API（winhttp.h）を用いて非同期にWikipedia API（ja.wikipedia.org）と通信します。サードパーティのHTTPライブラリを一切使わず、Windowsネイティブの高速なソケット接続を実現しています。

  • action=query&prop=extracts&explaintext=1: 記事本文のプレーンテキスト取得
  • action=parse&prop=text: 記事本文の完全なHTML/CSS取得（HTMLコース生成用）
  • rest.php/v1/page/{title}/media-list: 記事内の埋め込み画像一覧とサムネイルURL取得
  • action=query&prop=sections: 節構造（目次・見出しレベル）の取得
  • action=query&generator=random&prop=pageimages: ランダムな目標記事およびサムネイルの同時取得

5.2 SDOW（Six Degrees of Wikipedia）データベース構造

プロジェクトの Assets/data/jawiki_sdow-001.sqlite には、日本語版Wikipedia全記事の相互リンク関係がグラフデータベースとして格納されています。Git LFSやファイルサイズ制限に対応するため、リポジトリ内では part1〜part3 に3分割されており、CMakeビルド時に copy /b コマンドで自動結合されます。

テーブル / カラム 型 説明
pages.id INTEGER (PK) Wikipediaの記事ID
pages.title TEXT (UNIQUE) 正規化された記事タイトル（空白はアンダースコア）
links.id INTEGER (PK) 対象記事ID
links.outgoing_links TEXT その記事からリンクしている記事ID列（パイプ | 区切り）
links.incoming_links TEXT その記事へリンクしている記事ID列（パイプ | 区切り）

5.3 双方向BFS（Bidirectional Breadth-First Search）

記事Aから記事Bへの最短距離を計算する際、片方向の探索だとノード数が指数関数的に爆発（特に人気記事からの出力リンクは数千件に達する）するため、WikiShortestPath では双方向幅優先探索を採用しています。 

sequenceDiagram
  autonumber
  participant Caller as WikiPageLoader (Background Worker)
  participant ShortestPath as WikiShortestPath
  participant DB as SQLite3 (jawiki_sdow-001.sqlite)

  Caller->>ShortestPath: ComputeDistancesToTarget(links, targetId, maxDepth=4)
  ShortestPath->>ShortestPath: プロセス内キャッシュの確認 (同一targetIdの逆方向探索ツリー)
  alt キャッシュが存在しない場合
    ShortestPath->>DB: ターゲット側から逆方向BFSを実行 (Incoming links取得)
    DB-->>ShortestPath: 1手先、2手先の到達可能ノード集合
    ShortestPath->>ShortestPath: 逆方向ツリーをキャッシュ保存
  end
  ShortestPath->>DB: 候補リンク群のページIDを一括バッチ解決 (IN句チャンククエリ)
  DB-->>ShortestPath: ページID一覧
  ShortestPath->>ShortestPath: 順方向と逆方向ツリーの交差判定 (Intersection)
  ShortestPath-->>Caller: 各リンクのホップ数 (1手, 2手, 3手... 未到達=-1)
キャンセル安全性（Cancel Safety）の徹底

巨大なリンクを持つ記事の探索は数十秒かかる場合があります。プレイヤーが途中でウィンドウを閉じたり、別のシーンへ移動した際にメインスレッドがブロックされないよう、WikiShortestPath::RequestCancelAll() が実装されています。これはバックグラウンドから安全に sqlite3_interrupt() を発行し、実行中のクエリを即座に中断終了させます。

6. 地形生成 & HTML/CSSコースレンダリング（Terrain & HTML Course Rendering）

6.1 2つのコース生成方式：テキスト方式 vs HTML/CSS方式

WikiGOLFには、歴史的経緯と動作保証のために2つのコース生成方式が備わっています（CMakeオプション WIKIGOLF_HTML_COURSES で切替可能、既定値=ON）：

  • テキスト方式（従来）: 記事のプレーンテキストを均等に折り返してテクスチャ化。文字密度やキーワード（「山」「川」等）から簡易的なパーリンノイズハイトマップを生成。
  • HTML/CSS方式（新方式）: litehtml + Gumbo + DirectWrite + Direct2D により、記事のDOM構造（見出し、段落、表、画像、リンク）をそのままCSSレイアウトし、3D地形と1対1で同期。

7. 物理シミュレーション & Game Juice演出（Physics & Game Juice）

7.1 芝フリクションと静止摩擦判定（PhysicsFriction.h）

WikiGOLFの物理エンジンは、単純なクーロン摩擦ではなく、ゴルフボール特有の非線形な減速挙動を精密にシミュレートしています：

  • 低速域の粘り (ComputeSlowRollMultiplier): ボール停止間際になると転がり抵抗が非線形に増加し、現実のグリーン上のようにピタッと静止する（低速での永久振動を防止）。
  • 高速時の空気抵抗ブースト (ComputeHighSpeedBoost): 高速転がり時に芝抵抗が増加。
  • 斜面スケーリング (ComputeSlopeScale): 法線Y成分に基づき、急斜面では摩擦が低減して滑り落ちる。
  • 静止摩擦保持判定 (CanStaticFrictionHold): 傾斜による重力加速度と静止摩擦限界を比較し、緩斜面でボールが安定して止まるように判定。

7.2 バンカー特有の沈み込みシミュレーション

ボールがバンカーに着弾した際、鉛直衝突速度に応じて砂への沈み込み深さ（ComputeSurfaceSinkDepth）を計算します（最大でボール半径の約31%が砂に埋もれる）。さらに接線方向の運動量も ComputeSurfaceImpactTangentialRetention により半分以下に削られ、砂に「ズザッ」と突き刺さるようなリアルな感触を実現しています。

7.3 Game Juice（気持ちよさ・手応え）演出システム

「ゲームジュース（Game Juice）」とは、操作に対するフィードバックや快感を増幅する演出のことです。GameJuiceSystem が以下の演出を一括制御しています：

  • インパクト演出: Perfect/Greatショット時に画面全体がわずかに発光（Bloom Pulse）し、打球音と同時にカメラがシェイク。
  • ボールトレイル (TrailVS.hlsl): 高速飛行時にボール後方に美しい帯状の軌跡ポリゴンを描画。
  • カップイン発光 (CupIn Bloom): カップインの瞬間、カップ・旗・光柱がまばゆい金色に発光し、天使のファンファーレとともに紙吹雪（パーティクル）が舞い散る。
  • クリア時の花火（Hanabi Volley）: リザルト画面で打ち上げ花火が夜空に斉射され、炸裂光と火花パーティクルが自転する地球儀を照らし出す。

10.2 走査により判明した現状の課題と制約事項

  1. test_resource_manager_rules のDebugアサーション:

    調査中、Debugビルドにおいて test_resource_manager_rules.exe を実行した際、ResourcePool.h 128行目の assert(false && "Index out of range") が発火し、MSVCのGUIダイアログによってプロセスが停止する事象を確認しました。無効なハンドル（Invalid）を引数に取った際、Releaseビルドではフォールバックリソースを返す設計ですが、Debugビルドではアサーションで弾いているため、テストコード側の期待値との不一致が存在します（ReleaseビルドまたはCTest時の適切なフラグ調整が必要）。

  2. TAA（Temporal Anti-Aliasing）の未実装:

    SettingsScene および DisplaySettings に「TAA」のUIと設定保持が用意されていますが、内部コメントに記載されている通り「前フレーム情報・モーションベクトル等の基盤が必要なため、設定値として保持・永続化されるが描画には未反映」となっています。現在はMSAAおよびFXAAが主力です。

  3. 巨大記事におけるGPUメモリ消費:

    docs/html-course-rendering.md に記載されている通り、出力テクスチャの上限は32 Mi pixels（BGRA8で最大128 MiB）、キャッシュは最大2記事で128 MiBに制限されていますが、長大で画像が多数埋め込まれたWikipedia記事（例: 「日本」「第二次世界大戦」等）では、GPU VRAMとテクスチャ生成タイルの描画負荷が高くなります。

  4. 日本語禁則処理の簡易性:

    CourseHtml ではDirectWriteによる文字計測を行っていますが、完全なWebブラウザ水準の複雑な禁則処理（句読点の行頭配置禁止など）は一部簡易化されています。
