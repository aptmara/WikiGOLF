## 1. 通算打数を持つ(最優先)

### 問題

`TransitionToPage` が記事を移るたびに `state->shotCount = 0` に戻します。リザルトの `Shots`、評価、自己ベスト、デイリーランキング、実績に渡る打数は、すべて **最後の記事で打った数** だけです。遠回りして各記事で8打ずつ叩いても、最後の記事を1打で入れれば「1打」になります。

### 提案

`GolfGameState`(`WikiComponents.h:210`)を次のように分けます。

```cpp
int pageShots = 0;   // この記事で打った数(旧 shotCount。記事移動で0)
int totalShots = 0;  // ラウンド通算(記事移動でも戻さない)
std::vector<PageScore> scorecard; // 記事ごとの内訳
```

```cpp
struct PageScore {
  std::string page;
  int shots = 0;      // OB罰打込み
  int obCount = 0;
  int par = 0;        // 2章の「記事パー」
};
```

- 打つたび・OB のたびに `pageShots` と `totalShots` の両方を足す(`ShotController.cpp:277`、`WikiGolfSceneUpdate.cpp:596,639`)。
- 記事を出るとき(カップイン時)に `scorecard` へ1行積んでから `pageShots = 0`。
- `ResultData`、`AchievementEvent`、ランキング送信、自己ベストはすべて `totalShots` を使う。
- ホールインワン判定(`WikiGolfScene.cpp:210`)と実績「ホールインワン」は **記事ごと** の話なので `pageShots == 1` のまま。

名前を変えずに `shotCount` の意味だけ変えると、上の「記事ごと」の判定が静かに壊れます。いったん `shotCount` を消して、使っている箇所を全部コンパイルエラーで洗い出すのが確実です(`grep shotCount` で約20か所)。

### 「戻る」の扱い

Backspace で前の記事へ戻っても、`totalShots` はそのまま残します(戻る前に打った分は打った分)。戻ること自体に罰打をつけるかは、通算打数が入ってから実機で決めれば足ります。通算打数が入るだけで「遠回りは損」になるので、追加の罰はなくても成り立ちます。

## 2. パーを「ラウンドのパー」にする

### 問題

パーは記事を読むたびに `CalculateWikiGolfPar`(その記事からゴールまでの最小ホップ+1)で上書きされ、リザルトへはゴール直前の記事の値(1〜2)が渡ります。通算打数を入れても、比べる相手のパーが1〜2のままだと評価が全部「大叩き」になります。**1章と2章は同時に入れる必要があります。**

### 提案

**ラウンドパー** をスタート時に1回だけ決め、途中で変えません。

```
ラウンドパー = Σ(最短経路上の各記事の記事パー)
```

記事パーの決め方は2段階で考えます。

| 段階 | 記事パー | 長所 | 短所 |
|---|---|---|---|
| A(すぐ入る) | 一律 3 | 実装が数行。`ラウンドパー = 最短記事数 × 3` | 記事の広さ・カップの遠さを無視 |
| B(後で) | ティー→最短経路上のカップの距離で 3/4/5 | 「この記事 パー4」と言える。遷移演出の `パーN` 表示と合う | 地形生成後でないと決まらないので、ラウンドパーが記事を進むまで確定しない |

まず A で入れます。B はラウンドパーの「確定」と相性が悪いので、記事ごとの目安表示(HUD・スコアカード)にだけ使い、ラウンドパーは A のまま据え置くのが無難です。

実装メモ:

- 最短ホップ数は `WikiPageLoaderPath.cpp` が初回記事で求めている値をそのまま使える。`WikiGlobalData::initialPar`(`WikiComponents.h:104`)は宣言だけあって使われていないので、ここを `roundPar` と `shortestHops` に置き換える。
- ゴールへの経路がグラフに無い(`minHopsToTarget < 0`)ときは、いまのフォールバック(リンク数から3〜12)を流用し、「目安パー」と表示を変える。
- リザルトの経路比較(bf3694f)が出す最短経路と、ラウンドパーの元になる最短ホップ数が同じ値になっているか、テストで固定する。スタートの別名リダイレクト等で食い違うと「最短3記事なのにパー12」のような表示になる。

## 4. 実績の条件を直す

| 実績 | 現状の条件 | 問題 | 直し方 |
|---|---|---|---|
| 最短経路 | `hopCount == (par-2)*2` | 旧パー式の逆算。最後の記事のパー(1〜2)が渡るので常に 0 以下 → **解除不能** | `HoleCleared` に `shortestHops` を載せ、`hopCount == shortestHops` |
| バーディー級 | `shots <= par-2` | 最後の記事のパーで比べるので **実質解除不能**。しかも -2 はイーグル | 2章のラウンドパーで `totalShots <= roundPar - 1` にし、名前は「バーディー級」のまま。-2 用に「イーグル級」を別に足す |
| ワンパット感覚 | 毎回 `shots == par` | 説明の「(初回)」と合わない。名前とも合わない | 名前を「パーで回る」にして条件はそのまま、または「初回プレイで」の条件を本当に足す |

`ComputeMinimumHopsFromPar` は削除します。残すと、また誰かがパーから逆算しようとします。

`AchievementRules.h` は関数が小さく分かれているので、各条件に単体テストを1本ずつ足してから直すと安全です。

## 5. 自己ベストをコースごとにする

### 問題

`AchievementProgress::bestStrokes` が全コース共通の1個です。近いコースで1回良い数字を出すと、以後どのコースでも「記録更新」になりません。また更新判定が `WikiGolfScene.cpp:299` と `AchievementManager.cpp:135` に二重にあります。

### 提案

- `save/records.txt` に1行1コースで保存する。

  ```
  スタート記事|ゴール記事|モード\t最少打数\t最短時間ms\t最少記事数\t日付
  ```

  モード(通常/鬼)をキーに含めます。鬼モードの記録と混ぜない。
- 判定は `RecordStore::TryUpdate(key, result) -> 更新された項目の集合` の1か所に寄せ、リザルトの「NEW RECORD」と実績の両方がこれを見る。
- コース選択で同じ組を入れたとき「自己ベスト 14打 / 4記事」と出す。自由入力コースを繰り返し遊ぶ理由になります。
- 全体の `bestStrokes` は、コースをまたいで比べる意味がないので廃止してよい(実績で使っていなければ)。

## 6. デイリーチャレンジを公平にする

ランキングで順位をつける以上、全員が同じ条件で打つ必要があります。いま同じなのはゴール記事だけです。

| 要素 | 現状 | 提案 |
|---|---|---|
| スタート記事 | `list=random` で人ごと・やり直しごとに違う | `.linkgraph` からデイリーシードで引く。「ゴールまで最短3〜5ホップ」「被リンク数が一定以上」を満たすまで、同じシード列で引き直す。ネットワーク不要で全員一致 |
| 風 | `rand()` | `hash(デイリーシード, 記事名)` で決める。同じ記事なら誰でも同じ風 |
| クリア時間 | 読み込み・遷移演出中も加算(`WikiGolfSceneUpdate.cpp:65`) | `ScenePhase::Playing` の間だけ数える。回線速度で順位が変わらない |
| やり直し | 無制限 | ランキングに載るのは1日1回目だけ。2回目以降は「練習」として遊べるが送信しない |
| モード | 通常と鬼が同じ統計値に混ざる | デイリーは通常モード固定にするか、統計値を `daily_strokes` / `daily_strokes_oni` に分ける |
| セーフモード | ON/OFF でリンク集合が変わる | デイリーだけはフィルタを固定する |
| 打数の中身 | 最後の記事のぶん | 1章の `totalShots` |

ランキングの並びは「打数が少ない順、同打数なら時間が短い順」にします。PlayFab は統計値を1本ずつ並べるので、送る値を `打数 × 1,000,000 + 時間(0.1秒単位, 上限 999,999)` のような1本の合成値にすると、サーバー側の並べ替えだけで済みます。

不正対策は最小限でかまいませんが、CloudScript 側で `打数 ≥ たどった記事数`、`時間 ≥ 記事数 × 数秒` くらいは弾きます(送信値に記事数も足す)。

## 7. スコアを見せる

### 7.1 プレイ中の HUD

`CourseInfoPanel` は「現在の記事/ゴールの記事」だけで、打数もパーも出ません。1行足します。

```
3打目 ・ 通算 11打(パー9 / +2) ・ 4記事目
```

「この記事 パーN」は2章の段階Bを入れてから足せば十分です。

### 7.2 リザルトのスコアカード

1章の `scorecard` をそのまま表にします。bf3694f の経路比較画面と並べると、「どこで遠回りしたか」と「どこで叩いたか」が1画面で分かります。

```
記事             打数  OB
東京              4    0
江戸時代          6    1   ← 叩いた記事を色付け
徳川家康          2    0
-----------------------
通算             12   ラウンドパー 9 (+3) ボギー…
```

### 7.3 共有用の1行

デイリーの結果を Wordle のようにコピーできる文字列にします。打数と記事数だけで、記事名は出さない(ネタバレ防止)。

```
WikiGOLF 2026-11-12  12打(+3) / 4記事(最短3)
⛳🟩🟨🟥⛳
```

マスの色は記事ごとのパーとの差(2章の段階Bが入るまでは「1〜3打=緑、4〜5打=黄、6打以上=赤」の仮の閾値)。

## 8. 進め方

依存関係があるので、この順で入れるのが安全です。

| 順 | 内容 | 手間 | 依存 |
|---|---|---|---|
| 1 | 自己ベスト判定を1か所に寄せる(挙動は変えない) | 小 | — |
| 2 | `pageShots` / `totalShots` / `scorecard`(1章) | 小 | — |
| 3 | ラウンドパー段階A(2章)、評価名(3章) | 小 | 2 と同時に入れる |
| 4 | 実績条件の修正とテスト(4章) | 小 | 3 |
| 5 | HUD の打数表示(7.1) | 小 | 2, 3 |
| 6 | コース別記録(5章) | 中 | 1, 2 |
| 7 | デイリーの公平化(6章) | 中 | 2 |
| 8 | スコアカード・共有文字列(7.2, 7.3) | 中 | 2 |
| 9 | 記事パー段階B | 中 | 実機で調整 |

2〜5 は合わせても数日で、ここまで入れば「打数と経路の両方がスコアに出る」状態になります。6 はランキングを人に見せる前に必須です。

### 既存の記録の扱い

通算打数に変えると、今までの `BEST_STROKES` や送信済みのランキングとは意味が違う数字になります。

- `save/` の `BEST_STROKES` は読み捨てる(コース別記録へは移せない)。
- PlayFab の統計値は名前を変えて(例 `daily_strokes_v2`)新しく始める。古い値と混ぜない。
