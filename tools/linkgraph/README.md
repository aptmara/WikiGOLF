# リンクグラフの作り方（tools/linkgraph）

日本語版 Wikipedia のダンプから、WikiGOLF 用のリンクグラフファイル（`*.linkgraph`）を作る道具です。
旧来の SQLite（SDOW 形式, 約2.5GB）を置き換えました。ゲームは `Assets/data/jawiki.linkgraph` を
[WikiLinkGraph](../../src/game/systems/WikiLinkGraph.h) で読みます。ファイル形式の正確な定義は
[build_linkgraph.py](build_linkgraph.py) 冒頭の説明にあります。

## 使い方

```bash
python tools/linkgraph/build_linkgraph.py                       # 最新の完了済みダンプを取得して作る
python tools/linkgraph/build_linkgraph.py --offline              # 作業フォルダにあるダンプで作り直す
python tools/linkgraph/verify_linkgraph.py OUT.linkgraph --old-db Assets/data/jawiki_sdow-001.sqlite
```

- 必要なもの: Windows、Python 3.10 以降、numpy、CMake と C++ コンパイラ（MSVC で確認）
- できたファイルを `Assets/data/jawiki.linkgraph` に置けばゲームが使う（Git LFS で管理）
- 作業フォルダの既定は `%TEMP%/wikigolf-linkgraph`。ダンプ約5GB、pagelinks の展開に約4GB、中間ファイル数GB を使う
- C++ の `linkgraph_order` は初回に作業フォルダ内へ CMake で自動ビルドされる

## 設計の考え方

ゲームが必要とするのは「ある記事からゴールまで最短何手か」だけです。ゴールから入リンクを逆にたどる
幅優先探索（BFS）を1回すれば、全記事について答えが出ます。そのため:

- **入リンク一覧だけを持つ**。出リンク一覧・件数の列・リンクテーブルの重複表現は持たない
- 一覧は昇順の記事 ID を「前との差 - 1」にして LEB128 で並べ、16MiB ごとのフレームにして
  Windows 標準の Compression API（cabinet.dll）の LZMS で圧縮する。フレームごとに独立しているので
  並列に展開できる。zstd -19 より 5% ほど大きいが、ゲームに外部ライブラリが要らない
- **記事 ID を振り直す**: 再帰的グラフ二分割（Dhulipala ら, KDD 2016 の BP）で、似た相手からリンクされる記事を
  近い ID にする。差が小さくなるので、被リンク数順と比べて約39%小さい
- タイトル辞書は UTF-8 バイト順に並べ、64件ごとのブロックで前方圧縮してから LZMS（4MiB ごと）。転送ページのタイトルも含め、
  見出しバイトの最上位ビットで「転送ページかどうか」を示す（記事ID→本来のタイトルを引くため）

## 処理の流れと所要時間（32スレッド, jawiki-20261101）

| 工程 | 内容 | 時間 |
|---|---|---|
| 解析 | page / redirect / linktarget を並列に解析。pagelinks（gz で約1.5GB）は一度ファイルへ展開し、4MiB ずつの範囲を各プロセスが直接読む。数字は numpy でまとめて読む | 約56秒 |
| グラフ化 | 転送を最大5段まで解決して記事→記事にし、content_filter.tsv のレベル1（常時除外）を取り除く | 上に含む |
| 並べ替え（C++） | 重複除去、BP 二分割（20反復）、入リンク一覧の符号化 | 約73秒 |
| 書き出し | 各セクションをフレームに分け、並列に LZMS で圧縮して1ファイルへ | 約70秒 |

全体で約2分40秒（最初の素朴な版は約70分。うち numpy 版の BP が約49分）。
C++ の BP は、上の段は1つの分割を全スレッドで、下の段は共有の作業キューで分担する。
スレッド数を変えても出力は同じ（決定的）。

## できあがり（jawiki-20261101）

- 記事 1,520,522 件、リンク 141,381,210 本、タイトル 2,472,853 件（転送を含む）
- ファイル 126.5MB（LZMS）: 入リンク一覧 99.6 / タイトル 14.3 / タイトル→ID 6.1 / page_id 5.0 / 一覧の長さ 1.6 MB
  （zstd -19 なら 120.0MB）
- 年/月/日の記事・数字だけの記事もグラフに含める（ゲーム側の除外は別の仕組みで扱う）
- どのゴールにも全記事の 99.9% が5〜7手以内で届く
- ゲームでの読み込み 約0.5秒（全コアで展開。メモリ約250MB）、ゴール1つの逆向き BFS 約0.08秒
  （1スレッドなら約0.36秒）。以後の手数の問い合わせは表を引くだけ
- 旧 SQLite と最短手数を比べると 40組中38組が一致。違いはどちらも Wikipedia 側のリンクの変化

## 試して採らなかったもの

| 案 | 理由 |
|---|---|
| Elias-Fano / ビットマップ混在 | LEB128 + zstd に比べて得が小さく、仕組みが複雑 |
| LZMA | 少し小さいが展開に約7.6秒かかる |
| zstd の long モード | 1〜2% しか縮まない |
| BFS 順の ID | 被リンク数順より3%縮むだけ（BP は39%） |
| 同じ一覧の重複排除 | 該当が一覧の0.07%しかない |
| zstd（ゲームに同梱） | 5%小さいが、ゲームに外部ライブラリを足す必要がある。XPRESS_HUFF は速いが LZMS より約8%大きい |

## つまずいた点

- pagelinks の各 INSERT の最後の組は `);` で終わるので、`)` も区切りとして扱わないと次の行と数字がつながる
- numpy の `np.fromstring` は遅い（32MB で3.8秒）。桁の重みを使った一括変換で0.7秒
- 大きなブロックをプロセス間でパイプ送りすると詰まる。展開済みファイルを各プロセスが範囲で読む形にした
- 32プロセスで64MiB範囲だとメモリ不足。4MiB 範囲と int32 の作業配列にした
- dumps.wikimedia.org は同時取得が多いと 429 を返す。同時2本＋待って再試行
- MSVC は `/utf-8` がないと日本語コメントで壊れる

## 残っていること

- `content_filter.tsv` を最新データで作り直す（`build_filter_lists.py` は旧 SQLite の形式を読む）
- グラフでは「リンク先のタイトルが本文に出てくること」というゲーム側の選択条件は表せない
